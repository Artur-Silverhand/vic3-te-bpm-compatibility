# Быстрые обновления патча

Игроки используют обычные подписки Workshop: TE → полный BPM → патч.
Эта инструкция предназначена для сопровождения кода.

## 1. Что изменилось в установленной паре

```powershell
python .\tools\update_patch.py check
```

По умолчанию проверяются Workshop TE/BPM и установленная игра против закреплённой
базы. Отчёт: runtime/updates/report-check/report.md; полные данные — report.json.
Допустимы --timeline-root, --bpm-root (именно папки модов) и --game-root (папка игры).
`check --profile pinned` проверяет рабочую Git-базу вместо Workshop.

UNCHANGED — различий в проверенном объёме нет. RESTAGE_REQUIRED — только комментарии,
форматирование или переводы строк; нужны новые входные отпечатки и повторная проверка.
REVIEW_REQUIRED — изменён код/состав файлов, отсутствует достоверная старая версия
или изменена идентичность игры. Это список мест для работы, а не автоматический merge.
Ненулевой код выхода у check при изменениях ожидаем.

## 2. Проверить новые GitHub-ревизии

```powershell
python .\tools\update_patch.py upstream --fetch
```

Команда обновляет remote refs в исходных Git-клонах, показывает закреплённый commit,
доступный commit и имя ветки. Рабочие деревья не переключаются. Без --fetch читается
только уже имеющийся кеш. Имена веток брать из отчёта: у модов они могут различаться.

## 3. Подготовить отдельного кандидата

```powershell
python .\tools\update_patch.py stage --name update-001 --patch-version 0.7.0-dev --timeline-ref HEAD --bpm-ref HEAD --verify
```

HEAD воспроизводит текущую базу. Для обновления подставить remote refs из предыдущего
шага или точные SHA; --fetch при необходимости обновит refs перед подготовкой.
Можно указать --game-root для другой установленной версии игры.

Получается runtime/updates/update-001/project: собственные checkout модов, tools,
patch, новый sources.lock.json и отчёт об интеграционных пересечениях.
candidate.json содержит итог; verification.log — полный контроль; report.md — влияние
обновления. Существующий кандидат не перезаписывается: использовать новое имя.
Игра, playset, сохранения и установленный рабочий профиль не меняются.

## 4. Исправить конкретные несовместимости

Начать с same-path overrides и изменённых определений из report.md. Править адаптеры
в tools/ кандидата, добавлять контракт на изменённое поведение. Ошибки asserts при
изменении формата исходников требуют решения, а не удаления проверки ради PASS.

update-review.json перечисляет содержательные изменения и новые прямые пересечения.
Для каждого ID из required записать в reviewed конкретное решение и проверку.
Не удалять список required ради упаковки. Пока решения не записаны, даже SYNTHETIC_PASS
не разрешает упаковку/установку; статус кандидата — SYNTHETIC_PASS_REVIEW_REQUIRED.
После записи решений повторить контроль: файл решений также входит в отпечаток PASS.

Если обновилась игра: сначала проверить затронутый API/defines/scopes/hooks и новые
ванильные определения. После этого изменить supported_game_version в project.json
кандидата и повторить полный контроль. До пересмотра кандидат не получает PASS.

```powershell
Set-Location '.\runtime\updates\update-001\project'
python .\tools\verify_patch.py
python .\tools\package_patch.py
```

Упаковка повторно сверяет входы: обновление зависимости после PASS блокирует поставку.
Если ZIP этой версии уже существует и содержимое отличается, нужна новая patch_version.
Прежний архив не затирается. SYNTHETIC_PASS — офлайн-кандидат, не подтверждённый игровой
релиз. Игровые сценарии выполняет пользователь через Steam.

Для публикации обновления использовать прежний Workshop item ID: записать его в
workshop_id файла project.json или передать --workshop-id подготовщику release/prepare_workshop.py.
Подготовщик выводит этот ID для поля загрузчика; сам в Steam ничего не отправляет.
Если изменились родительские моды, создать полный новый тестовый профиль через
prepare_local_profile.py; обновление только патча в старом профиле будет заблокировано.

Проверенные изменения затем переносить в основной проект: tools, project.json, update-review.json,
новый lock/research report и результаты. Личные paths.local.json, runtime-логи,
рабочие checkout и резервные копии в Git не отправлять.
